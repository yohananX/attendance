## M6 — Health endpoint rate limiting: deferred with residual risk

**Decision:** Rate limiting on `/api/health` is **deferred**, not implemented.

**Defensible reasons:**
1. The endpoint is already protected by the `x-health-secret` operator header (401 without a valid secret), which materially reduces the unauthenticated DoS surface (S1/S3 addressed).
2. A 5-second `AbortController` timeout bounds each call (S4 partially addressed).
3. The platform (Vercel serverless) is stateless; an in-memory rate limit would not survive across invocations and would not protect against distributed probing. A meaningful rate limit requires a shared store (Redis/Upstash) or edge config, which is out of scope for T1.2 and would add infrastructure not in the pilot contract.
4. Health is an operational probe, not a high-traffic user endpoint; expected call volume is low.

**Residual risk:** An attacker who obtains or guesses the `HEALTH_CHECK_SECRET` can issue repeated health calls to (a) probe database connectivity timing and (b) contribute to application-layer DoS. The secret mitigates but does not eliminate this. **Mitigation:** rotate `HEALTH_CHECK_SECRET` periodically; monitor health endpoint error rates; revisit rate limiting when a shared cache/store is introduced (post-pilot). This is an accepted, documented residual risk for the controlled pilot.

## Remaining blockers

1. **No non-production Supabase project / credentials.** `.env.local` contains only `VERCEL_OIDC_TOKEN`; `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are unset. The migration **must not** be applied to production and cannot be applied to a non-production project without credentials. **Unblock:** stakeholder provisions a non-production Supabase project and injects `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `HEALTH_CHECK_SECRET`, `SESSION_SECRET`, `STAFF_PIN` into `.env.local`/Vercel; then apply the migration and verify connectivity via `/api/health`.
2. **Sandbox blocks loopback TCP binding** (EACCES on `127.0.0.1`), so a scratch Postgres cannot be bound locally to execute the 9 skipped DB-integration tests. They will run once `DATABASE_URL` points at a reachable Postgres/Supabase instance.
3. **Q5, Q13, Q14, Q15, Q16 remain Pending.** These are stakeholder questions, not T1.2 code defects; they gate T2.x (ingest validation window, corrections online-only, day-close blocking, WhatsApp wording, residual-risk acknowledgement). PD-D1 is implemented as a configurable default pending Q5 confirmation.
4. **T2 not begun.** Per instructions, no T2 implementation started.
