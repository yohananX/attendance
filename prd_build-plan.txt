School Attendance Sign-In: PRD and Build Plan
30 Oct 2026 · @Someone
Overview
This is a small web app that records when each child arrives at and leaves Saturday's extra lesson, so the school can send every parent timestamped proof. Staff type a name and a parent number, tap Sign in, later tap Sign out, then send the parent a WhatsApp message.
The app is a success if every child present has an arrival and a departure time that staff cannot type or alter, and every parent receives that proof the same day.

Goals, non-goals and success criteria
The app must produce believable proof of arrival and departure with the least typing possible at the gate.
Goals
• Record a child's arrival in under 15 seconds.
• Record departure with one tap from a list of children currently in school.
• Set every time on the server, so staff cannot type or back-date it.
• Give staff a ready-to-send WhatsApp message for each parent.
Non-goals for Saturday
• Parent logins or a parent portal.
• QR cards or barcode scanning.
• Automatic SMS or WhatsApp sending.
• Fees, grades, timetables or any wider school management.
Success criteria
• Every child present on Saturday has one row with a sign-in time, and a sign-out time once they leave.
• No row can have its sign-in time changed after it is saved.
• Every parent receives a message with both times before the day ends.
• Two staff phones can use the app at once without losing or duplicating records.
Users and roles
Only school staff use the app. Parents never log in; they only receive a message.

Screens and flows
The app has two screens and one small edit window. It is designed for a phone held in one hand, with large buttons.
Screen 1: Login
• Fields: first name, PIN.
• Button: Log in.
Screen 2: Attendance (one page, three parts)
1. Sign in form at the top: student name, parent phone, Sign in button. After saving, the form clears and the name is ready for the next child.
2. In school list: each row shows name, sign-in time and a Sign out button.
3. Signed out today list: each row shows name, both times, a Send message button, and a "Message sent" marker once used.
A search box above the lists filters by name. A small counter shows how many children are in school now.
Edit window: opens from a pencil icon on any row. It changes name and phone only and shows the times as read-only text.
Daily flow
1. Child arrives. Staff type name and parent phone, then tap Sign in.
2. Child appears in "In school".
3. Child is collected. Staff tap Sign out on that row.
4. Row moves to "Signed out today".
5. Staff tap Send message. WhatsApp opens with the text ready.
6. Staff tap send in WhatsApp. The app marks the message as sent.

Run this in the Supabase SQL editor:
create extension if not exists pgcrypto;

create table attendance (
  id uuid primary key default gen_random_uuid(),
  student_name text not null,
  parent_phone text not null,
  signed_in_at timestamptz not null default now(),
  signed_out_at timestamptz,
  signed_in_by text not null,
  signed_out_by text,
  message_sent_at timestamptz,
  created_at timestamptz not null default now()
);

create table attendance_edits (
  id uuid primary key default gen_random_uuid(),
  attendance_id uuid not null references attendance(id),
  edited_by text not null,
  old_name text,
  new_name text,
  old_phone text,
  new_phone text,
  edited_at timestamptz not null default now()
);

-- Lock the times: sign-in can never change, sign-out can be set once.
create or replace function lock_attendance_times() returns trigger as $$
begin
  if new.signed_in_at is distinct from old.signed_in_at then
    raise exception 'signed_in_at cannot be changed';
  end if;
  if old.signed_out_at is not null
     and new.signed_out_at is distinct from old.signed_out_at then
    raise exception 'signed_out_at is already set';
  end if;
  if new.signed_out_at is not null and old.signed_out_at is null then
    new.signed_out_at := now();
  end if;
  return new;
end;
$$ language plpgsql;

create trigger attendance_lock_times
before update on attendance
for each row execute function lock_attendance_times();

-- No deletes through the app.
create or replace function block_attendance_delete() returns trigger as $$
begin
  raise exception 'attendance rows cannot be deleted';
end;
$$ language plpgsql;

create trigger attendance_no_delete
before delete on attendance
for each row execute function block_attendance_delete();

-- Failed PIN attempts, used for the 5-minute wait.
create table login_attempts (
  id uuid primary key default gen_random_uuid(),
  device text not null,
  attempted_at timestamptz not null default now()
);

-- Turn on row level security with no public policies.
alter table attendance enable row level security;
alter table attendance_edits enable row level security;
alter table login_attempts enable row level security;
To sign a child out, the app sets signed_out_at to any value. The trigger replaces it with the database clock, so the time is always the server's. With row level security on and no policies, the public key in the browser can read or write nothing. Only the server, using the service role key, can reach the tables.
Security and privacy
The app holds children's names and parents' phone numbers, so access must be limited to staff and the database must not be reachable from the open internet.
• PIN check on the server. The browser sends the PIN to a server route. The server compares it with a secret setting and, if it matches, sets a signed, HTTP-only cookie that lasts 12 hours.
• No database keys in the browser. All reads and writes go through server code using the Supabase service role key. That key lives only in Vercel environment variables.
• Row level security on, no policies. This blocks the public Supabase key from reading or writing anything.
• Limit PIN guessing. After 5 wrong PINs from one device, wait 5 minutes before allowing another try.
• Use a PIN of at least 6 digits and change it after Saturday. Share it by word of mouth, not in a group chat.
• HTTPS only. Vercel provides this automatically.
• Attribution. Staff first name is saved on each sign-in and sign-out. A shared PIN cannot prove who typed it, so this is a record of who said they did it.
• Retention. Keep the records until the end of term, then export and delete them. Tell parents what is recorded and why when the message is first sent.
Technical architecture
The phone never talks to the database directly. Every request goes to the Vercel app, which alone holds the database key.
The parent message leaves from the staff phone through WhatsApp, not from the server, so the app needs no messaging account.
Choices
• Framework: Next.js (App Router) with server actions for sign in, sign out and edits.
• Database access: @supabase/supabase-js in server code only, using the service role key.
• Login session: a signed, HTTP-only cookie holding the staff first name.
• PIN limit: failed attempts are counted per device in a small login_attempts table.
• Time display: formatted in Africa/Lagos with Intl.DateTimeFormat, so every phone shows the same time.
• WhatsApp link: https://wa.me/<number without +>?text=<url-encoded message>.
• Refresh: the lists reload every 15 seconds and after each action, so both staff phones stay in step.

Deployment steps
1. Supabase. Create a project. Pick the region closest to Lagos (a Europe region such as London or Frankfurt is usually nearest). Save the database password somewhere safe.
2. Run the SQL from the Data model section in the SQL editor.
3. Copy two values from Project Settings, then API: the project URL and the service_role key. Never paste the service role key into front-end code or a chat.
4. GitHub. Push the Next.js project to a private repository.
5. Vercel. Import the repository and add these environment variables:
    ◦ SUPABASE_URL
    ◦ SUPABASE_SERVICE_ROLE_KEY
    ◦ STAFF_PIN (6 digits or more)
    ◦ SESSION_SECRET (a long random string)
    ◦ SCHOOL_NAME (used in the parent message)
6. Deploy. Open the Vercel URL on a phone and log in.
7. Add to home screen on each staff phone so the app opens like a normal app.
8. Set the Vercel function region near your Supabase region so each tap is fast.
